# Схема машинной проекции screens.yaml

Схема — контракт концепта интерфейса: его пишет навык функционального владельца в режиме концепта, а читает тот, кто делает макет (`ROLE-DEVELOPER`), и архитектор, которому концепт задаёт техническую рамку. Меняется только вместе с версией плагина.

Концепт отвечает на вопрос «что где стоит и что с этим можно сделать», а не «как это выглядит». Он не вводит новых объектов: всё, что показано на экране, уже есть в `domain.yaml`, а то, чего там нет, попадает в отдельный массив `unbound` и остаётся видимым пробелом. Разметка положений — те же три оси плюс автор формулировки (см. `statuses.md`).

## Верхнеуровневые поля документа

| Поле | Назначение |
|---|---|
| `product_id` | Идентификатор продукта — тот же, что в `description.yaml` и `domain.yaml`. |
| `screens_version` | Номер версии концепта для человеческого чтения. |
| `document_status` | Статус документа: черновик / незавершённый черновик. |
| `date` | Дата текущей версии. |
| `based_on_domain_version` | Версия `domain.yaml`, по которой построен концепт. Обязательно: концепт показывает объекты модели, и без версии неизвестно, каких именно. |
| `based_on_research_version` | Версия `research.yaml`, если исследование было. **Отсутствует целиком**, если концепт строился без исследования. |

## Массив `layout`

Оболочка: как устроено пространство экрана. Одна запись на экран либо одна на общую оболочку, если экраны её делят.

| Поле | Назначение |
|---|---|
| `id` | Идентификатор компоновки (`LY-001`). |
| `name` | Наименование компоновки. |
| `zones` | Список зон — см. ниже. |

### Зона

| Поле | Назначение |
|---|---|
| `id` | Идентификатор зоны (`ZN-001`). |
| `name` | Наименование зоны на русском языке. |
| `placement` | Где зона стоит — словами: `слева`, `справа`, `сверху`, `снизу`, `центр`. Не координаты и не проценты: концепт задаёт расположение, а не размеры. |
| `orientation` | `вертикально`, `горизонтально` либо поле отсутствует, если ориентация для зоны бессмысленна. |
| `persistent` | `true`, если зона остаётся видимой при работе в других частях экрана. У вложенной зоны поле не указывается: постоянство наследуется от родительской — вложенная зона не может быть постоянной внутри непостоянной и наоборот. Каждая `persistent: true` зона покрывается запросом архитектору: постоянная видимость — техническое условие, а не только продуктовое пожелание. Один запрос может покрывать несколько зон, если техническое условие у них общее. |
| `contains` | Список идентификаторов вложенных зон (`ZN-…`). Пустой список, если вложенных нет. |
| `pattern` | Идентификатор паттерна (`PT-…`) из исследования, если зона устроена по разобранному паттерну. Отсутствует, если решение своё или исследования не было. |

## Массив `screens`

| Поле | Назначение |
|---|---|
| `id` | Идентификатор экрана (`SC-001`). |
| `name` | Наименование экрана. |
| `purpose` | Зачем экран нужен — одной фразой, на языке предметной области. |
| `layout` | Идентификатор компоновки (`LY-…`). |
| `scenario_steps` | Список шагов сквозного сценария, которые проходят через этот экран, в форме `E2E-001#3`. Экран, не привязанный ни к одному шагу, — повод спросить, зачем он: концепт строится по сценарию, а не по воображению. |
| `zone_content` | Содержание зон — см. ниже. |

Плюс общие поля разметки.

### Содержание зоны

| Поле | Назначение |
|---|---|
| `zone` | Идентификатор зоны (`ZN-…`). |
| `objects` | Список того, что в зоне показано — см. ниже. Пустой список допустим сам по себе: зона может быть объявлена раньше, чем наполнена, и это не дефект. Когда в каркасе появляется пометка «(нет объекта)», задаёт не эта схема, а правило рендера в `domain-output-format.md`: пометку получает зона, у которой пробел **установлен**, а не та, до которой не дошла очередь. |

### Объект в зоне

| Поле | Назначение |
|---|---|
| `object` | Идентификатор объекта предметной модели (`OBJ-…`). **Только существующий в `domain.yaml`.** |
| `states_visible` | Список состояний этого объекта, которые видны пользователю в этой зоне. Каждое — из списка `states` объекта в модели. |
| `actions` | Список действий над объектом в этой зоне — см. ниже. |

### Действие

| Поле | Назначение |
|---|---|
| `id` | Идентификатор действия (`AC-001`), уникальный в пределах документа. Нужен затем, чтобы запрос архитектору о переходе мог сослаться на конкретное действие, а не описывать его словами. |
| `name` | Что делает пользователь — глаголом предметной области, а не названием элемента управления. |
| `to_state` | Состояние объекта, в которое действие его переводит. Из списка `states` этого объекта. Отсутствует, если действие состояния не меняет. |
| `to_screen` | Идентификатор экрана (`SC-…`), на который действие уводит. Отсутствует, если переход не происходит. Каждый переход между экранами, требующий технического решения — встраивание, навигация поверх встроенного, — порождает запрос архитектору. |

## Массив `unbound`

Элементы, которые собеседник хочет видеть на экране, но за которыми нет объекта предметной модели.

| Поле | Назначение |
|---|---|
| `id` | Идентификатор (`UB-001`). |
| `zone` | Зона, в которой элемент предполагался (`ZN-…`). |
| `text` | Что именно просили, как сказано. |
| `resolution` | Куда это ушло: идентификатор открытого вопроса либо запроса роли. Пустым не бывает — иначе элемент просто теряется. |

Сюда же попадает всё, что относится к уровню исполнения: размеры, цвета, поведение элементов управления, визуальный язык. Это не концепт (`ROLE-DEVELOPER` в границах концепта), и в `zone_content` такие записи не попадают никогда.

## Массивы `open_questions`, `role_requests`, `attachments`, `process_references`

Состав полей — как в `description-schema.md`. У открытого вопроса поле `addressed_to` обязательно и здесь.

## Массив `findings_state`

Появляется, когда в режим приложено заключение к гейту с находками по этому документу. Состав полей — как в `description-schema.md`: `finding_id` (`F-…`), `state` («закрыта изменением» | «закрыта отказом» | «не закрыта» | «не закрыта, роль не назначена»), `resolved_by` (список идентификаторов, которыми находка закрыта; у незакрытой — пустой список), `note` (обязательна при отказе). Массив живёт в дорабатываемом документе, а не в заключении: заключение принадлежит давшей его роли, и навык его не меняет. Порядок разбора — блокирующие находки первыми, правила приёма — в `incoming-documents.md`.

## Инварианты

**Каждый `objects.object` существует в `domain.yaml`.** Концепт не заводит объектов: если на экране нужно то, чего в модели нет, это `unbound`, а не новая запись. Объект появляется в модели в режиме предметной модели, и только после этого — в зоне.

**Каждое значение `states_visible` и `to_state` есть в списке `states` того же объекта в `domain.yaml`.** Состояние, которого у объекта нет, показать нельзя, а перевести в него — тем более.

**Элемент без объекта — только в `unbound`, никогда в `zone_content`.** Это тот же запрет, что и первый, с другой стороны: `zone_content` описывает модель на экране, `unbound` — то, что моделью пока не покрыто.

**У каждой записи `unbound` поле `resolution` непусто.** Пробел, о котором не заведено ни вопроса, ни запроса, через неделю неотличим от забытого.

**Каждое действие с `to_screen` имеет `id`.** Переход между экранами — кандидат в запрос архитектору, и запрос ссылается на идентификатор действия, а не пересказывает его.

**`linked_statement` запроса из концепта указывает на экран (`SC-…`), а не на зону.** Разметку — `type`, `confirmation_status` — несёт экран; у зоны их нет, и менять по ответу роли у зоны нечего. Зона, ради которой запрос заведён, называется в тексте запроса: там она видна и человеку, и при разборе ответа.

**Каждая зона с `persistent: true` покрыта запросом архитектору** — своим либо общим с другими зонами. Постоянная видимость при работе во встроенной области — техническое условие, и одна роль его не решает. Вложенные зоны в проверке не участвуют: их постоянство задаёт родительская.

## Идентификаторы

`LY-`, `ZN-`, `SC-`, `AC-`, `UB-`, `OQ-`, `RR-`, `AT-` — префиксы устойчивых идентификаторов. Идентификатор сохраняется между версиями документа, при изменении текста не меняется, удалённый повторно не используется.

**Ссылка на шаг сквозного сценария записывается как `E2E-<номер>#<порядковый номер шага>`** — например, `E2E-001#3`: третий шаг в массиве `steps` сценария `E2E-001`. Собственных идентификаторов у шагов в `domain-schema.md` нет, поэтому шаг адресуется парой «сценарий и позиция».

Ключи полей — латиницей; значения трёх осей и значения `placement` и `orientation` — на русском языке; идентификаторы и коды ролей — без кавычек.
