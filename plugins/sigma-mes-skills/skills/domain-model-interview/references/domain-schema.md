# Схема машинной проекции domain.yaml

Схема — контракт между навыками ролей: её пишет навык функционального владельца, а читает всякий, кому нужна предметная модель, — прежде всего навык архитектора, которому она задаёт объекты, состояния и их авторитетные источники. Меняется только вместе с версией плагина.

`domain.yaml` — проекция той же модели, что и `domain.md`, а не пересказ текста. Экспорт в YAML не может: повысить статус подтверждения относительно того, что зафиксировано в модели; добавить положение, которого в модели нет; заполнить поле, которое в модели пусто. Разметка положений — те же три оси плюс автор формулировки, что и в продуктовом описании (см. `statuses.md`); здесь описано только то, чем предметная модель от продуктового описания отличается.

## Верхнеуровневые поля документа

| Поле | Назначение |
|---|---|
| `product_id` | Идентификатор продукта — тот же, что в `description.yaml`. Своего идентификатора у предметной модели нет: она описывает тот же продукт. |
| `domain_version` | Номер версии предметной модели для человеческого чтения. С версией описания не связан и своим темпом не обязан ей соответствовать. |
| `document_status` | Статус документа: черновик / незавершённый черновик. |
| `date` | Дата текущей версии. |
| `constitution_revision` | Редакция Конституции СИГМА.MES+, на которую опирается версия. |
| `based_on_description_version` | Версия `description.yaml`, по которой построена модель. Обязательно: предметная модель без указания входа не проверяема — неизвестно, какие продуктовые решения она разворачивает. |

Владелец смысла области указывается в шапке `domain.md` со слов пользователя и отдельного верхнеуровневого поля не имеет: владелец назначается объекту, а не документу (см. `terms-registry.md`, `TERM-SEMANTIC-OWNER`, и OPEN-QUESTIONS.md, вопрос 14).

## Общие поля разметки

Поля ниже есть у элементов `objects`, `domain_rules` и у сценария — везде, где записано положение предметной модели.

| Поле | Назначение |
|---|---|
| `type` | Тип содержания — ось 1, значения из `statuses.md`. |
| `confirmation_status` | Статус подтверждения — ось 2, значения из `statuses.md`. |
| `approved_by` | Код роли, утвердившей положение. Присутствует ТОЛЬКО при статусе «утверждено ответственной ролью»; в предметной модели принимает значение `ROLE-FUNCTIONAL-OWNER`. |
| `awaiting` | Адресат заключения — ось 3, объект с полями `role` и `module`. Присутствует ТОЛЬКО при статусах «ожидает заключения роли» и «ответ роли зафиксирован». |
| `source` | Ссылка на источник — обязательна при статусе «ответ роли зафиксирован». |
| `formulated_by` | Автор формулировки: пользователь или ИИ. |
| `related` | Список идентификаторов связанных элементов модели. Присутствует всегда; если связей нет — пустой список `[]`. |
| `terms` | Список идентификаторов записей массива `terms` (`TC-…`), критичных для смысла этого положения. Присутствует всегда; если критичных терминов нет — пустой список `[]`. |
| `part` | Часть модели, к которой относится элемент: `objects`, `rules`, `scenario` или `terms`. Аналог поля `section` в продуктовом описании: положение вне четырёх частей не записывается. |

## Массив `objects`

Критичные производственные объекты (`TERM-CRITICAL-BUSINESS-OBJECT`) — то, ошибка в определении или жизненном цикле чего искажает планирование, исполнение, качество, НЗП, прослеживаемость или аналитику.

| Поле | Назначение |
|---|---|
| `id` | Устойчивый идентификатор объекта (`OBJ-001`). Сохраняется между версиями: при изменении определения объект не получает новый идентификатор. |
| `name` | Предпочтительное русское наименование объекта. |
| `definition` | Определение объекта: что именно им считается и что не считается. |
| `states` | Список имён состояний объекта. Состояние (`TERM-STATE`) — признанное положение объекта на момент времени, а не произвольный статус интерфейса. Пустым список не бывает: объект без состояний либо не критичен, либо его жизненный цикл ещё не разобран — и тогда это открытый вопрос, а не пустое поле. |
| `state_basis` | По каким установленным фактам и правилам объект признаётся находящимся в каждом из состояний. Здесь различаются пять видов события: намерение, команда, состояние, наблюдение и производственный факт (`terms-registry.md`). Формулировка вида «состояние меняется, когда оператор нажал кнопку» в это поле не записывается: нажатие — команда, а признание состояния требует правила. |
| `semantic_owner` | Код роли — владельца смысла объекта (`TERM-SEMANTIC-OWNER`). Как правило `ROLE-FUNCTIONAL-OWNER`. Записывается со слов пользователя; при двух и более названных владельцах одного объекта заводится открытый вопрос, и выбор за пользователя не делается. |
| `authoritative_state_source` | Авторитетный источник состояния (`TERM-AUTHORITATIVE-STATE-SOURCE`): система или область, уполномоченная задавать состояние в определённом периоде и контексте. Значения: «не определено» либо названное пользователем. Поле ведётся совместно с `ROLE-ARCHITECT`, поэтому положение о нём **никогда не стоит в статусе «утверждено ответственной ролью»** — его статус всегда «ожидает заключения роли» или «ответ роли зафиксирован». |

Плюс общие поля разметки. Полномочие источника не доказывает достоверность записи: качество и происхождение данных проверяются отдельно (`TERM-DATA-PROVENANCE`).

## Массив `domain_rules`

Предметные правила — условия над объектами, сохраняющие смысл при смене технологии.

| Поле | Назначение |
|---|---|
| `id` | Устойчивый идентификатор правила (`DR-001`). |
| `text` | Текст правила на русском языке. |
| `objects` | Список идентификаторов объектов (`OBJ-…`), которых правило касается. Пустым не бывает: правило без объекта не проверяемо. |

Плюс общие поля разметки. Предметное правило — не общее правило Конституции (`TERM-COMMON-RULE`): общее действует для нескольких команд, модулей или этапов и живёт в Конституции, предметное описывает поведение объектов одной функциональной области. Правило, которое по существу оказалось общим, в `domain_rules` не записывается — оно адресуется `ROLE-PROCESS-OWNER`.

## Объект `scenario`

Один сквозной производственный сценарий (`TERM-END-TO-END-SCENARIO`) — последовательность от основания или события до проверяемого результата через необходимых участников, объекты, модули и внешние границы. Сценарий один: второй сквозной сценарий — это отдельная предметная модель или отдельный разговор, а не второй элемент массива.

| Поле | Назначение |
|---|---|
| `id` | Идентификатор сценария (`E2E-001`). |
| `name` | Наименование сценария. |
| `maturity` | Зрелость сценария. На Инициации принимает единственное значение «последовательность и границы» (`RULE-SCENARIO-001`): на этом этапе проверяются порядок шагов и внешние границы, а не исполнение. Значения других этапов на Инициации не ставятся. |
| `steps` | Упорядоченный список шагов. Порядок значим: он и есть последовательность. |

Плюс общие поля разметки — у сценария в целом.

### Шаг сценария

| Поле | Назначение |
|---|---|
| `actor` | Кто выполняет шаг: роль процесса, производственная роль со слов пользователя либо внешняя система. |
| `action` | Что происходит на шаге. |
| `objects` | Список идентификаторов объектов (`OBJ-…`), затронутых шагом. |
| `boundary` | Внешняя граница: наименование внешней системы или области, за которую сценарий выходит на этом шаге. Поле отсутствует, если шаг границы не пересекает. Граница — не украшение схемы: именно она отделяет ответственность продукта от чужой. |

## Массив `terms`

Словарь функциональной области. Состав записи — контракт из `terms-registry.md`, раздел «Запись термина», полностью: `id`, `term`, `technical_id`, `definition`, `synonyms`, `scope`, `owner_role`, `source`, `term_status`, `check_result`. Отличие от `term_candidates` продуктового описания — в заполненности `definition`, а не в составе полей: здесь определение заполняется, и `term_status` может принимать значение `approved`. `scope`, `owner_role` и `source` обязательны и здесь — как в любой записи термина.

`approved` ставится только по явному утверждению носителем роли, по одному термину, и только когда у записи заполнены `definition`, `scope` и `owner_role`. Термину уровня Конституции и межмодульному термину этот навык `approved` не ставит ни при каких условиях: их утверждает `ROLE-PROCESS-OWNER`.

Поле `part` у записи словаря — `terms`.

Сверх контракта реестра запись словаря несёт `formulated_by` — «пользователь» либо «ИИ». Поле не украшение: утверждение термина требует, чтобы определение написал пользователь, а не навык (ограничение 3 в `statuses.md`), и без этого поля проверить условие после возобновления сессии нечем — в памяти его нет, а из текста определения автор не виден.

## Массив `findings_state`

Состояние работы по находкам приложенного заключения к гейту. Состав полей и правила — те же, что в `description-schema.md`, включая четвёртое значение `state` «не закрыта, роль не назначена»; в предметной модели массив появляется, когда заключение с находками, адресованными `ROLE-FUNCTIONAL-OWNER`, приложено в режим изменения.

## Массивы `open_questions`, `role_requests`, `attachments`, `process_references`

Состав полей — как в `description-schema.md`, с одной заменой: вместо `section` используется `part` со значениями `objects`, `rules`, `scenario`, `terms`. У процессных вопросов поле `part` отсутствует, как и `section` в продуктовом описании.

## Инвариант связи

Каждое положение со статусом «ожидает заключения роли» или «ответ роли зафиксирован» имеет ровно одну запись в `role_requests`, у которой `linked_statement` равен идентификатору этого положения — `OBJ-…`, `DR-…` или `E2E-…`. Запись создаётся в том же ходе интервью, что и статус. Положение с заполненным `awaiting`, но без парной записи, — дефект разметки: адресат без запроса означает, что роль ни о чём не попросили.

Отсюда прямое следствие для `authoritative_state_source`: поскольку это поле всегда стоит в ролевой очереди, у каждого объекта с названным или неопределённым авторитетным источником есть запрос к `ROLE-ARCHITECT`. Объект без такого запроса — незавершённая разметка.

Обратное не требуется: запрос роли может существовать без связанного положения. Процессные вопросы — неназначенная роль, расхождение о правиле, применимость схемы модулей — в `role_requests` не пишутся ни при каких условиях: их место `open_questions`.

## Идентификаторы

`OBJ-`, `DR-`, `E2E-`, `TC-`, `OQ-`, `RR-` — префиксы устойчивых идентификаторов. Идентификатор сохраняется между версиями документа и при изменении текста не меняется; удалённый идентификатор повторно не используется. Ключи полей — латиницей; кириллические ключи в YAML запрещены. Значения-перечисления трёх осей записываются на русском языке в двойных кавычках и дословно как в `statuses.md`; латинские технические значения — коды ролей, номера модулей, `term_status`, `check_result`, `part` — без кавычек.
