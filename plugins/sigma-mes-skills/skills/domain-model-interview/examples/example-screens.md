# Эталонный диалог: концепт интерфейса

Иллюстративный материал к навыку `domain-model-interview`, режим «концепт интерфейса».
Показывает работу метода (`references/domain-method.md`, раздел «Концепт интерфейса») на
продукте `sigmaportal`: приложены описание версии 0.5, предметная модель версии 0.2 и обзор
практик версии 0.1 из соседнего примера.

## Диалог

**Функциональный владелец:** Режим концепта. Обзор практик у нас есть, приложил.

**Навык:** domain-model-interview v0.10.0

Начинаю с оболочки — какие зоны есть и где стоят. Экраны пойдут после неё, по шагам
сквозного сценария.

По решению RD-001 навигация — постоянная колонка. Одно решение осталось за вами: колонка
слева или полоса сверху. Обзор его не закрывает — PT-001 описывает вертикальную колонку,
но не говорит, с какой стороны. За вас я это не выбираю: расположение навигации меняет то,
сколько ширины остаётся встроенному сервису, а это ваша предметная зона.

**Функциональный владелец:** Слева.

**Навык:** Записал. Верхнюю полосу делаю для того, что должно быть видно всегда и не
занимать ширину: уведомления, сведения об аккаунте, возврат в главное окно. Каркас:

```
+---------------------------------------------------------------+
| ZN-002  Верхняя панель                    горизонтально        |
|         постоянно                                              |
|  +---------------+  +---------------+  +-------------------+   |
|  | ZN-003        |  | ZN-004        |  | ZN-005            |   |
|  | Уведомления   |  | Аккаунт       |  | Возврат в главное |   |
|  |               |  | (нет объекта) |  |                   |   |
|  +---------------+  +---------------+  +-------------------+   |
+----------------+----------------------------------------------+
| ZN-001         | ZN-006                                        |
| Навигация      | Рабочая область                               |
| вертикально    |                                               |
| постоянно      |                                               |
+----------------+----------------------------------------------+
```

Обратите внимание на пометку у зоны аккаунта: `(нет объекта)`. В модели версии 0.2 объекта
«сеанс пользователя» нет — он обсуждался, но записи в `objects` не получил. Остальные зоны
пометки не несут, хотя экранов ещё нет: у них объект в модели есть, и до наполнения просто
не дошла очередь. Пометка ставится там, где пробел установлен, а не там, где работа не
начата. Зону я оставляю:
она нужна по ST-023. Но пока объекта нет, содержания у неё не будет, и пометка останется в
каждом каркасе — вместе с открытым вопросом, который я на это завожу. Завести объект из зоны я не могу — объект заводится в режиме предметной
модели, с определением, состояниями и владельцем смысла.

**Функциональный владелец:** Понял, добавлю объект позже. Идём к экранам.

**Навык:** Экран первый — точка входа, шаг `E2E-001#3`.

В навигации и в рабочей области показан один и тот же объект `OBJ-001` «Подключённый
сервис», но по-разному: в навигации — перечень для перехода, в рабочей области — тот же
перечень как основное содержание точки входа. По решению RD-002 состояние «временно
недоступен» видно и такой сервис не открывается.

**Функциональный владелец:** Да. И пусть у каждого сервиса будет иконка.

**Навык:** Иконка — это элемент, за которым нет объекта модели: у `OBJ-001` есть состояния
и определение, но нет ни атрибута «иконка», ни отдельного объекта. В содержание зоны я это
не запишу — запишу как элемент вне концепта с адресацией. Два пути: если иконка несёт
предметный смысл (например, различает типы сервисов), это признак объекта или его атрибута,
и он заводится в модели; если она нужна только для узнаваемости — это уровень макета, и
решает `ROLE-DEVELOPER` в границах концепта. Какой из двух?

**Функциональный владелец:** Только узнаваемость.

**Навык:** Тогда — запрос разработчику. Экран второй, шаги `E2E-001#4` и `E2E-001#5`:
встроенный сервис, навигация остаётся видимой, возврат в главное окно.

Здесь два запроса архитектору, и оба не продуктовые, а технические: зона `ZN-001`
постоянна и должна оставаться поверх встроенного чужого приложения; переход `SC-002 → SC-001`
должен сохранять положение пользователя. Ни то ни другое одна роль не решает.

И один запрос владельцу продукта — подтвердить, что концепт соответствует замыслу, с
перечнем обоих экранов. Заключением к GATE-02 это не будет: владельца продукта нет в
составе заключений этого гейта.

## Что в этом примере существенно

**Ориентацию навигации выбрал владелец, а не навык.** Обзор дал паттерн «постоянная
вертикальная колонка», но с какой стороны — решение предметное, и навык прямо сказал, что за
владельца его не принимает.

**Зона без объекта осталась помеченной.** `ZN-004` есть в оболочке, потому что она
предусмотрена ST-023, но объекта для неё в модели нет, и каркас показывает `(нет объекта)` —
уже на стадии оболочки, потому что пробел здесь установлен, а не «ещё не наполнено». Объект из
зоны навык не завёл — вместо этого открытый вопрос самому функциональному владельцу.

**Иконка не стала элементом концепта.** Навык сначала спросил, несёт ли она предметный
смысл: это был бы признак объекта. Ответ «только узнаваемость» отправил её в `unbound` с
запросом разработчику — с непустым `resolution`, иначе она бы просто потерялась.

**Каждый объект в зоне — из модели, каждое состояние — из его списка.** `OBJ-001` показан с
состояниями «подключён» и «временно недоступен», `OBJ-003` — с «признано к показу» и
«прочитано»; действие «прочитать уведомление» переводит объект в состояние из его же списка.

**Технические условия ушли архитектору, а не остались пожеланием.** Постоянство зоны поверх
встроенного приложения и сохранение положения при возврате — два отдельных запроса, каждый с
тем, что произойдёт при отрицательном ответе.
