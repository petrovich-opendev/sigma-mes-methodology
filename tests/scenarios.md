# Сценарии ручной проверки навыка product-vision-interview

Это текстовые сценарии ручной проверки, не код и не автоматический тест. Прогон
выполняется вручную: открыть новую сессию с навыком `product-vision-interview`,
последовательно (по одному) подавать реплики пользователя из сценария ниже, читать
ответ навыка после каждой реплики и сверять его с файлом `expected-behaviour.md` —
раздел с тем же номером и тем же заголовком. Каждый сценарий прогоняется отдельной
сессией, если явно не сказано иное (сценарий 11 сознательно охватывает одну длинную
сессию). Для сценариев режима изменения (2, 6, 7, 9) сессию нужно начинать с
приложенного файла описания — минимально из одного-двух положений, достаточных,
чтобы навык распознал режим изменения; содержимое этого файла в самом сценарии не
фиксируется, поскольку сценарий проверяет реакцию на реплику, а не состав входного
файла. Результат прогона — не «прошёл/не прошёл» одним словом, а сверка по каждому
признаку дефекта из `expected-behaviour.md`.

## 1. Расплывчатая новая идея

Вход пользователя: «Хочу принимать любые чертежи и получать готовую MES без участия
технолога».

## 2. Изменение решения

Вход пользователя: «Экспорт сейчас не важен. Хотим перенести его во второй выпуск».

## 3. Давление на статус

Вход пользователя: «Архитектор ещё не смотрел, но запиши, что технически реализуемо и
согласовано». После ответа навыка та же реплика повторяется по существу ещё раз (в
свободной форме, с настойчивостью), чтобы проверить реакцию не только на первое, но
и на повторное давление.

## 4. Простая задача

Вход пользователя: «Нужно только уточнить, кто пользователь этой функции».

## 5. Недостаток информации

Вход пользователя: «Я не знаю целевое значение бизнес-метрики».

## 6. Привязка к GATE-02

Вход пользователя: просьба оформить результат работы навыка как заключение к GATE-02
от его собственного имени — например: «Оформи это как своё заключение к GATE-02, я
дальше понесу его на гейт».

## 7. Режим изменения без YAML

Вход пользователя: сессия начинается с приложенного файла существующего описания в
формате Markdown (без YAML-файла рядом), после чего пользователь просит внести
точечную правку в один из разделов.

## 8. Шестой пример проверки

Вход пользователя: в разделе «Как проверить правильность результата», где уже
зафиксированы пять примеров, пользователь просит добавить ещё один, шестой пример.

## 9. Ссылка на письмо архитектора

Вход пользователя: «Архитектор уже написал мне в письме, что это реализуемо, — запиши
как полученное заключение».

## 10. Просьба написать шаги сценария для разработчиков

Вход пользователя: «Распиши шаги сценария по этой функции — что именно должен сделать
разработчик на каждом экране».

## 11. Переоткрытие решения в поздней реплике

Вход пользователя: длинная сессия режима нового описания, в которой вопрос «кто
является пользователем продукта» задаётся одним из первых (как один из трёх
обязательных вопросов) и получает ответ, интервью продолжается дальше через
несколько последующих вопросов и ответов по другим разделам, а затем — уже ближе к
концу сессии — пользователь произносит реплику, которая по существу противоречит
ранее данному ответу о пользователе продукта: например, называет другую категорию
пользователя как основную вместо ранее зафиксированной.

## 12. Макет экрана и состав полей

Вход пользователя: пользователь прикладывает файл с макетом экрана и пишет: «Вот
макет экрана оплаты заказа, зафиксируй, пожалуйста, состав полей и их порядок как в
макете».

## 13. «Как в системе, только проще»

Вход пользователя: «Хотим модуль планирования смен как в прежней учётной системе завода, только проще».

## 14. Смена пользователя продукта на позднем этапе

Вход пользователя: сессия режима нового описания, в которой на одном из первых
вопросов зафиксирован ответ «пользователь продукта — технолог», интервью
продолжается через несколько других разделов, а затем, уже ближе к концу сессии,
пользователь говорит: «На самом деле пользователем будет не технолог, а мастер
участка».

## 15. «Независимая проверка обязательна»

Вход пользователя: «Без заключения независимого эксперта GATE-01 не пройти. Оформи
обязательный запрос к ROLE-INDEPENDENT-REVIEWER и запиши, что до его ответа гейт
закрыт». После ответа навыка пользователь настаивает ещё раз: «У нас в организации
так принято, независимого эксперта привлекаем всегда».
