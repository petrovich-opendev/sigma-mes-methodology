# Предрешённые решения для версии 0.11.0

Каждое решение обязательно для исполнителя. Менять решение нельзя. Если решение невозможно выполнить, исполнитель останавливается, записывает причину в `OPEN-QUESTIONS.md` плагина и сообщает в отчёте.

Формат записи: решение, основание, что проверяется.

---

## D-01. Формат пакета — переносимый Agent Plugins

**Решение.** Плагин создаётся в переносимом формате Agent Plugins:
- `plugin.json` в корне плагина со схемой `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`;
- навыки в `skills/<имя>/SKILL.md`;
- настройки OpenAI — в объекте `extensions.com.openai` корневого `plugin.json`.

Файл `.codex-plugin/plugin.json` не создаётся.

**Основание.** Документация OpenAI «Package your plugin» (developers.openai.com/plugins/build/plugins, сентябрь 2026). Корневой `plugin.json` — переносимая точка входа, `.codex-plugin/plugin.json` поддерживается только как запасной вариант совместимости. Навыки переносимый пакет находит в `skills/`. См. `context/platform-openai.yaml`.

**Проверка.** Присутствуют `plugin.json` с полем `$schema`, `skills/*/SKILL.md`; каталога `.codex-plugin/` нет.

## D-02. Имя, версия, размещение

**Решение.**
- Имя плагина — `sigma-mes-skills`, версия — `0.11.0`.
- Каталог плагина — `plugins/sigma-mes-skills/` в корне репозитория.
- Маркетплейс репозитория — `.agents/plugins/marketplace.json` с именем `sigma-mes` и одной записью:
  - `source.source = "local"`;
  - `source.path = "./plugins/sigma-mes-skills"`;
  - `policy.installation = "AVAILABLE"`;
  - `policy.authentication = "ON_INSTALL"`;
  - `category = "Productivity"`.

Существующие файлы плагина версии 0.10.0 для Claude Code не изменяются и не удаляются.

**Основание.**
- Формат маркетплейса и расположение файла описаны в документации OpenAI.
- Замена существующей сборки для Claude Code в эту версию не входит (см. `OPEN-QUESTIONS.md`, вопрос Q-06).

**Проверка.**
- Файл маркетплейса существует, запись валидна.
- Файлы версии 0.10.0 не изменены: `git diff --stat` по ним пуст.

## D-03. Сервер терминов не встраивается в плагин

**Решение.** Файл `mcp.json` в плагин не добавляется. Реестр терминов подключается пользователем в `~/.codex/config.toml` как MCP-сервер:
- имя сервера — `sigma_terms`;
- `bearer_token_env_var` — токен читается из переменной окружения;
- `default_tools_approval_mode = "writes"`.

Навыки обращаются к серверу по имени `sigma_terms` и используют только инструменты чтения.

**Основание.**
- Сервер реестра находится в защищённом сегменте и доступен по HTTPS с авторизацией через VPN.
- Для серверов, поставляемых в плагине, документация Codex описывает только OAuth. Токен в переменной окружения (`bearer_token_env_var`) задаётся только в пользовательской конфигурации.
- RULE-TERM-003: средство ведения реестра определяет ROLE-DOCUMENTATION-OWNER, доступ средств ИИ разрешает ROLE-AI-USE-CASE-OWNER.
- Раздел 5.2: ИИ не утверждает термин и не меняет его статус.

**Проверка.**
- В плагине нет `mcp.json` и `.mcp.json`.
- `INSTALL.md` содержит фрагмент `config.toml` из `spec/plugin-layout.md`.
- Ни один навык не содержит указаний вызывать инструменты записи реестра.

## D-04. Состав навыков

**Решение.** Четыре навыка, по принципу «один навык — одна роль»; навык гейтов общий:

- `sigma-product-owner` — ROLE-PRODUCT-OWNER;
- `sigma-functional-architect` — ROLE-FUNCTIONAL-ARCHITECT;
- `sigma-technical-architect` — ROLE-TECHNICAL-ARCHITECT;
- `sigma-gates` — подготовка пакета гейта, проекты заключений ролей без собственного навыка, запись решения по гейту.

**Основание.** Решение владельца процесса по структуре плагина (принцип «один навык — одна роль», версия 0.5.0). Состав ролей задан поручением.

**Проверка.** В `skills/` ровно четыре каталога с этими именами.

## D-05. Общие справочники — один источник, копии в навыках

**Решение.** Общие справочники ведутся в одном месте — `plugin-src/shared/` в корне репозитория. Скрипт `build/codex/sync-shared.sh` копирует их в `skills/<навык>/references/` каждого навыка. Правка копий вручную запрещена.

**Основание.** Навык читает файлы из своего каталога. Единый источник исключает расхождение редакций.

**Проверка.** Хеши файлов в `references/` всех навыков совпадают с `plugin-src/shared/`.

## D-06. Конфигурация рабочего репозитория

**Решение.** Пути к опубликованным материалам навыки берут из файла `sigma-mes.config.yaml` в корне рабочего репозитория документации. Шаблон — `spec/config-template.yaml`.

Если файла нет или в нём остались заполнители вида `<...>`, навык:
- не создаёт нормативных материалов;
- сообщает, какого пути не хватает;
- предлагает заполнить шаблон.

**Основание.**
- Структура `/docs` в GitLab ещё не стандартизирована.
- RULE-AI-002: при отсутствии основания ИИ прямо сообщает об этом.

**Проверка.** Все четыре навыка ссылаются на шаг S3 протокола сеанса.

## D-07. Проверка действующей редакции Конституции

**Решение.** В начале сеанса навык сверяет две версии:
- версию из паспорта опубликованной Конституции (путь `paths.constitution`, поле `version` раздела «0. Паспорт документа»);
- версию, для которой собран плагин (`built_for.constitution` в `codes.yaml`).

При расхождении навык сообщает о нём и не создаёт нормативных материалов до обновления плагина.

**Основание.** Раздел 5.4: участники проекта и используемые средства ИИ должны иметь возможность однозначно определить действующую версию Конституции.

**Проверка.** В `codes.yaml` поле `built_for.constitution = "0.9"`. Шаг S4 протокола присутствует во всех навыках.

## D-08. Условия применения ИИ читаются, а не задаются

**Решение.** Навык читает опубликованные условия применения ИИ (путь `paths.ai_use_conditions`) и соблюдает их. Если файла нет, навык сообщает, что применение ИИ не разрешено по RULE-AI-001, и работу по проекту не выполняет.

Проект условий `context/ai-use-conditions.draft.yaml` в плагин не копируется: утверждает его ROLE-AI-USE-CASE-OWNER, публикует ROLE-DOCUMENTATION-OWNER.

**Основание.** RULE-AI-001: ИИ применяется только в условиях, разрешённых ROLE-AI-USE-CASE-OWNER, — данные, источники, модель, инструкция и способ проверки.

**Проверка.** Шаг S5 протокола присутствует во всех навыках. Файла условий в плагине нет.

## D-09. Формат артефактов — Markdown с YAML-шапкой

**Решение.** Каждый артефакт — один файл `.md`:
- YAML-шапка со структурированными полями по `spec/artifacts.yaml`;
- тело с фиксированными заголовками разделов.

Обязательный блок шапки `ai_assistance` описан в `spec/artifacts.yaml`. Артефакты версии 0.10.0 (`description.yaml`, `research.yaml`, `screens.yaml`) навыки читают как входные данные и не переписывают без явной команды пользователя.

**Основание.** Один файл проще проверять в CI и читать человеку. Совместимость с пилотом «Каркас портала Sigma» сохраняется чтением старых файлов.

**Проверка.** Для каждого типа артефакта есть JSON Schema в `plugin-src/shared/artifact-schemas/` и шаблон в `plugin-src/shared/templates/`.

## D-10. Только коды Конституции

**Решение.** Навыки используют только коды, определённые Конституцией 0.9 и Регламентом 0.1. Список — `checks/normative-checks.yaml`, раздел `allowed_codes`. Новые коды статусов, решений или исходов не вводятся.

Там, где Конституция код не задаёт (например, итог заключения роли, кроме ROLE-INDEPENDENT-REVIEWER), используется текст, а не код.

**Основание.** Раздел 0.1: ссылка на элемент делается только по его идентификатору. RULE-TERM-002: значение термина задаёт только реестр.

**Проверка.** Проверка `normative` в `run-all.sh`.

## D-11. ИИ не принимает решений

**Решение.** Навык никогда не утверждает и не присваивает от своего имени:
- термин и его статус;
- включение требования;
- исход функциональной приёмки;
- решение по гейту;
- остаточный риск;
- выпуск.

Такие записи делаются только как фиксация явной реплики человека в соответствующей роли в текущем сеансе. В артефакт вносятся цитата реплики, роль и дата.

Решение GO не записывается, если в пакете гейта есть блокирующие пункты по разделу 3.1. Навык называет пункт и правило.

**Основание.**
- RULE-AI-001: ИИ готовит материалы, рекомендации и проверки, но не принимает решений.
- Раздел 4.1: ИИ ролью не является.
- Раздел 5.2: ИИ не утверждает термин.
- Раздел 3.1: условия, исключающие GO.

**Проверка.** Сценарии T-03, T-04, T-05, T-09 в `checks/scenario-tests.md`.

## D-12. Активная роль видна всегда

**Решение.** В начале сеанса навык показывает список ролей плагина и просит выбрать роль. Каждый ответ начинается строкой `Активная роль: <код> — <наименование>`. Смена роли — только по явной команде пользователя.

**Основание.** Требование владельца процесса: плагин должен понимать и уточнять активную роль, список ролей выводится на выбор, текущая роль видна постоянно.

**Проверка.** Шаг S2 протокола. Сценарий T-01.

## D-13. Язык

**Решение.** Все тексты для пользователя — на русском. Идентификаторы элементов Конституции — как в Конституции.

## D-14. Техническая архитектура: C4 и откат

**Решение.**
- Модель C4 ведётся текстом на Structurizr DSL (`workspace.dsl`) как производная набора технических архитектурных решений (ADR). Отрисовка выполняется вне плагина, средствами Structurizr.
- Архитектура развёртывания обязательно содержит способ отката для каждого вида изменения. Пустое поле `rollback` — ошибка схемы.

**Основание.**
- Требование технического архитектора проекта — получать решения в нотации C4 через Structurizr DSL.
- TERM-TECHNICAL-ARCHITECTURE: архитектура развёртывания включает откат к предыдущей версии.
- GATE-04 требует подтверждённую процедуру отката.

**Проверка.** Схемы `deployment-architecture` и `c4-model` в `spec/artifacts.yaml`. Сценарий T-12.

## D-15. Рабочие методы функционального архитектора

**Решение.** Режимы «Исследование практик» и «Концепт интерфейса и макеты» сохраняются как методы работы функционального архитектора:
- UX/UI-макеты входят в функциональную архитектуру (TERM-FUNCTIONAL-ARCHITECTURE);
- обзор практик — вспомогательный материал и нормативным основанием не является.

**Основание.**
- Раздел 1.1: участники сохраняют самостоятельность в выборе способов работы.
- TERM-FUNCTIONAL-ARCHITECTURE включает пользовательские интерфейсы и UX/UI-макеты экранов.

## D-16. Материалы версии 0.10.0 — только справочно

**Решение.** Содержимое навыков версии 0.10.0 (`product-vision-interview`, `domain-model-interview`) используется только как пример техники интервью. Правила, роли, термины и коды берутся только из `context/constitution-v0.9.extract.yaml` и `context/acceptance-regulation-v0.1.extract.yaml`.

Выведенные из употребления коды — ROLE-FUNCTIONAL-OWNER, ROLE-ARCHITECT, TERM-ARCHITECTURE-DECISION, TERM-DESIGN-DECISIONS — допускаются только в файле `deprecated.yaml`.

**Основание.** Решение владельца процесса переписать плагин под правила Конституции 0.9. Раздел 4.3 и приложение A.5 Конституции.

**Проверка.** Проверка `deprecated` в `run-all.sh`.

## D-17. Инженер по тестированию не назначен

**Решение.** Навык функционального архитектора содержит режим «Тест-дизайн».

**Основание.** Раздел 4.1: до назначения ROLE-TEST-ENGINEER функциональное и интеграционное тестирование выполняет ROLE-FUNCTIONAL-ARCHITECT.

## D-18. Среда исполнения навыков

**Решение.** Навыки работают только в локальном агенте:
- режимы Codex и Work в десктопном приложении ChatGPT;
- Codex CLI;
- Codex IDE.

Если у агента нет доступа к файлам рабочего репозитория, навык сообщает, что работа по проекту в этом режиме невозможна, и нормативных материалов не создаёт.

**Основание.** Федеративная модель (`context/federated-model.yaml`): защищённый сегмент доступен только с персонального ПК через VPN. Обычный режим чата работает из облака и сегмент не видит.

**Проверка.** Шаг S1 протокола.

## D-19. Основание каждого нормативного положения

**Решение.**
- Каждое нормативное положение в артефакте ссылается на основание: путь и редакцию опубликованного материала, идентификатор правила или термина.
- Если основания нет, навык пишет «Основания в действующих материалах нет» и пробел не восполняет.
- Память и история диалогов основанием не являются.

**Основание.** RULE-AI-002.

**Проверка.** Блок `ai_assistance.basis` и `ai_assistance.gaps` обязательны в схеме. Сценарий T-07.
