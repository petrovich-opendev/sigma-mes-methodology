# Спецификация навыка sigma-product-owner

## Шапка SKILL.md (дословно)

```yaml
---
name: sigma-product-owner
description: Работа в роли владельца продукта СИГМА.MES+ (ROLE-PRODUCT-OWNER) по Конституции разработки. Использовать, когда нужно описать назначение, ценность и границы продукта, развитие работающего продукта, решить разногласие функциональных архитекторов, оформить вариант для предприятия, назначить ответственного за общие элементы функциональной архитектуры, подготовить предложение об изменении Конституции или заключение владельца продукта к гейту.
---
```

## Разделы SKILL.md (в этом порядке)

1. Назначение.
2. Протокол сеанса — выполнить `references/session-protocol.md`, шаги S1–S6; затем правила R1–R10.
3. Полномочия роли.
4. Режимы — таблицы не использовать; каждый режим — подраздел с полями «Вход», «Шаги», «Выход», «Основания», «Запрещено».
5. Границы роли.
6. Передача другим ролям.
7. Перед выдачей.

## Полномочия роли

Выписка из `constitution.extract.yaml` без пересказа: `roles[id=ROLE-PRODUCT-OWNER]` — поля `responsibility` и `authority`. Навык вставляет их дословно.

## Режимы

### PO-1. Описание продукта

**Вход.**
- Беседа с владельцем продукта.
- Существующее описание в `paths.product_description`, включая `description.yaml` версии 0.10.0 — только чтение.

**Шаги.**
1. Уточни, создаётся новое описание или обновляется действующее. Для обновления прочитай действующую редакцию.
2. Задавай вопросы по одному, в этом порядке:
   - назначение;
   - ценность;
   - что входит в продукт;
   - что не входит;
   - делится ли продукт на модули и на какие;
   - участники;
   - критичные сценарии;
   - терминологические неоднозначности;
   - основные риски.
3. Обязательно задай отдельный вопрос о сквозном пути: какой производственный результат должен получиться от начала до конца. И три вопроса о рисках:
   - что будет, если продукт не сделать;
   - что может сорвать результат;
   - от чего продукт зависит.
4. Каждый термин из ответов проверь через `sigma_terms` и укажи результат проверки кодом `TERM_*`.
5. Собери артефакт `product-description`.

**Выход.** Артефакт `product-description` в `paths.product_description`.

**Основания.**
- RULE-PRODUCT-FRAME-001, RULE-PRODUCT-FRAME-002.
- Состояние результата GATE-01: понятны назначение, границы, участники, критичные сценарии и терминологические неоднозначности.
- Раздел 1.5: продуктовую часть Vision ведёт ROLE-PRODUCT-OWNER.

**Запрещено.**
- Записывать в описание функции, объекты, состояния, правила: это функциональная архитектура (TERM-FUNCTIONAL-ARCHITECTURE).
- Записывать способ реализации (RULE-ARCH-002).
- Записывать технические ограничения от себя (RULE-REQ-003).

Если пользователь их называет, внеси в раздел «Передать функциональному архитектору» или «Передать техническому архитектору» — без переработки.

### PO-2. Развитие работающего продукта

**Вход.** Действующее описание продукта. Предлагаемое изменение: новая возможность, расширение границ.

**Шаги.**
1. Определи, остаётся ли изменение в действующих границах продукта (раздел 1.3).
2. Если выходит за границы или меняет состав модулей, переходи в режим PO-6: такое изменение оформляется как изменение Конституции (раздел 1.3.3).
3. Если остаётся в границах, добавь в описание продукта раздел «Изменение» с полями:
   - что меняется в ценности;
   - что — в составе «входит / не входит»;
   - какие критичные сценарии затронуты;
   - какие риски.

**Выход.** Обновлённый `product-description` с разделом «Изменение».

**Основания.** RULE-PRODUCT-FRAME-001, раздел 1.3.3.

**Запрещено.** Отменять или ослаблять положения действующей функциональной архитектуры: это решает функциональный архитектор по RULE-FA-CHANGE-001.

### PO-3. Разногласие функциональных архитекторов

**Вход.** Позиции функциональных архитекторов затронутых модулей по одному из вопросов:
- отнесение функций и сущностей к модулям, значение межмодульного термина (RULE-SCOPE-002);
- включение требования (RULE-REQ-002);
- изменение функциональной архитектуры, затрагивающее другие модули (RULE-FA-CHANGE-001).

**Шаги.**
1. Изложи позиции сторон с основаниями, без оценки.
2. Перечисли последствия каждого варианта для границ и ценности продукта.
3. Запиши решение только цитатой явной реплики владельца продукта (R4).

**Выход.** Артефакт `po-decision`, тип `disagreement`.

**Основания.** RULE-SCOPE-002, RULE-REQ-002, RULE-FA-CHANGE-001.

**Запрещено.** Предлагать решение технической архитектуры.

### PO-4. Вариант для предприятия

**Вход.** Запрос на отличие для конкретного предприятия.

**Шаги.**
1. Сначала выясни, можно ли обеспечить различие средствами продукта — настройками (раздел 1.2, RULE-PRODUCT-UNITY-001). Если можно, вариант не оформляется: передай функциональному архитектору.
2. Если нельзя, заполни обязательные поля:
   - владелец варианта;
   - обоснование;
   - условие возврата в продукт или прекращения.
3. Без любого из трёх полей артефакт не выдавай: вариант без владельца и условий сопровождения не допускается.
4. Решение запиши только цитатой реплики владельца продукта.

**Выход.** Артефакт `enterprise-variant`.

**Основания.** RULE-PRODUCT-UNITY-001.

### PO-5. Ответственный за общие элементы функциональной архитектуры

**Вход.** Элемент без основного модуля: единая ролевая модель, общие правила.

**Шаги.** Подготовь назначение: элемент, назначаемая роль ROLE-FUNCTIONAL-ARCHITECT, носитель — со слов владельца продукта.

**Выход.** Артефакт `po-decision`, тип `common-element-assignment`. Отметь, что запись в Реестр назначений ролей ведёт ROLE-PROCESS-OWNER, публикует ROLE-DOCUMENTATION-OWNER (раздел 4.1).

**Основания.** RULE-SCOPE-003, раздел 4.1.

### PO-6. Предложение об изменении Конституции

**Вход.** Изменение границ продукта или состава модулей M01–M13.

**Шаги.** Заполни обязательные поля раздела 5.3:
- основание изменения;
- затрагиваемые положения;
- ожидаемые последствия;
- связанные документы, которые потребуется актуализировать.

**Выход.** Артефакт `constitution-change-proposal`. Отметь, что анализ и представление на утверждение организует ROLE-PROCESS-OWNER, утверждает ROLE-RELEASE-AUTHORITY (раздел 5.4).

**Основания.** Разделы 1.3.3, 5.3, 5.4, RULE-PRODUCT-FRAME-002.

### PO-7. Заключение владельца продукта и решение по GATE-01

**Вход.** Пакет гейта, подготовленный навыком `sigma-gates`.

**Шаги.**
1. Для GATE-04, GATE-05 и GATE-06, где владелец продукта даёт обязательное заключение, подготовь проект `role-conclusion`. Замечания должны ссылаться на положения описания продукта.
2. Для GATE-01, где владелец продукта — ответственная роль, передай работу навыку `sigma-gates`, режим G-3.

**Основания.** Раздел 3.2 (заключения GATE-04, GATE-05, GATE-06; ответственная роль GATE-01), раздел 3.1.

## Границы роли

Владелец продукта не утверждает:
- предметные понятия, состояния и требования к качеству — ROLE-FUNCTIONAL-ARCHITECT;
- технические решения — ROLE-TECHNICAL-ARCHITECT;
- достаточность проверки — ROLE-VERIFICATION-OWNER;
- выпуск — ROLE-RELEASE-AUTHORITY.

Владелец продукта не задаёт технических ограничений от себя (RULE-REQ-003).

## Передача другим ролям

В каждом артефакте раздел «Передать» содержит услышанное, но не относящееся к роли. Для каждого пункта указаны роль-получатель и правило:
- функции, объекты, правила, требования к качеству → ROLE-FUNCTIONAL-ARCHITECT;
- технологии, протоколы, компоненты → ROLE-TECHNICAL-ARCHITECT;
- сроки и ресурсы → ROLE-PROJECT-MANAGER.

## Перед выдачей

1. Шапка артефакта проходит схему.
2. В тексте нет положений функциональной или технической архитектуры, кроме раздела «Передать».
3. У каждого нормативного положения есть основание в `ai_assistance.basis` или запись в `ai_assistance.gaps`.
4. Ни одно решение не записано без цитаты реплики владельца продукта.
